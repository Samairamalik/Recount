# Learning log
One line per session: something I learned, or a question an interviewer would ask about what I built today.
Sunday ritual: (1) did this week's milestone-state come to exist? (2) what could I be interviewed on? (3) any stop-and-reconsider trigger active?

- 2026-09-06 — Stage 0, design consequence 1/3: **direction/sign must be a checked field** on growth and comparison claims. Motivating case from the spike: "Fourth-quarter revenue declined by 43.61%" verified as PASS, because the comparator checked magnitude only and never read "declined" — the true change was +43.61%. A false accept on a claim asserting the opposite of the truth. Interviewer question: how does your verifier tell a wrong magnitude apart from a correct magnitude with an inverted sign?
- 2026-09-06 — Stage 0, design consequence 2/3: **`subject` is first-class on every claim type**, not just `ranking`. 13 of 39 extracted claims had spans naming no entity at all ("336,300.71 in total revenue"); the structured `subject` field was the sole carrier. Span-local verification would have computed the national figure and produced 13 false flags.
- 2026-09-06 — Stage 0, design consequence 3/3: **extractor recall is weakest on non-numeric claims**. Of 13 genuine extraction misses, 9 were the direction-only comparisons, the rankings, and the vague growth — every claim with no number in the sentence. Since several of those are deterministically checkable, that is lost coverage, not correct abstention. Per spike/RESULTS.md.
- 2026-09-06 — Stage 1, BINDING Stage 3 requirement (a): **better/worse comparisons require metric polarity** (`polarity` in SemanticConfig) and must abstain `schema_gap` when it is absent. Fixture c17 "delivery performance improved" is only checkable because the config says lower `avg_delivery_days` is better; a silent higher-is-better default would be a false-accept path. Not implemented in Stage 1.
- 2026-09-06 — Stage 1, BINDING Stage 3 requirement (b): **ranking `group_by` may name a time grain** ("quarter", "month", "year"), resolved from `time_column`, not from `entities`. Fixture c23 "peak fulfillment efficiency of the year" ranks quarters by `avg_delivery_days` and must NOT abstain as `schema_gap`. Not implemented in Stage 1.
- 2026-09-06 — Stage 1: a Pydantic discriminated union dispatches on one literal field (`type`) before validating anything else, so an unknown type fails fast with a one-line error instead of five overlapping ones, and mypy narrows `Claim` to the exact class after an `isinstance`. Interviewer question: why `extra="forbid"` on a contract that sits between an LLM and a verifier?
- 2026-09-06 — Stage 2, AMENDMENT (visible, not silent): `AbstainReason` gained a fourth value, `NO_DATA`, for an empty slice, a zero growth baseline, or a ranking subject absent from the groups. The Stage 1 freeze was on the corruption taxonomy, not this enum; the enum's design rule is "grouped by what the user can do about it", and NO_DATA's action ("your data does not cover this period/entity") is distinct from unsupported type, schema gap and vagueness. It is the only reason the engine (not the compiler) raises.
- 2026-09-06 — Stage 2: a SQL prepared statement can bind values but never identifiers, so "one parameterized template per plan type" is honest only with the rule spelled out: column names are rendered from the plan after the loader validated them against the real schema and execute() re-checks them; keywords (SUM/AVG/COUNT, ASC/DESC, the optional entity clause) come from Literal fields; everything data-shaped is a bound parameter. Also: the half-ulp comparison is done in Decimal because 12.555 - 12.55 in floats is not 0.005. Interviewer question: why can't `$column` be a parameter, and what would go wrong if you quoted it yourself without the schema check?
- 2026-09-06 — Stage 3, AMENDMENTS (visible, not silent), decided while reviewing docs/abstention.md row by row: (1) `Ranking.scope: str | None` — the ranking universe as written ("of the year" → "2017"); a time-grain ranking with no scope abstains `ambiguous` rather than inferring a calendar year (G8). (2) `Comparison.value` is `ge=0` like Growth: sign lives only in `direction`, so a sign/direction conflict is impossible by construction. (3) Fixture relabels: c1 PASS → UNVERIFIABLE/schema_gap (no `state_count` metric, no COUNT DISTINCT; deferred), c11 gains `displaced: "unspecified"` and its reason becomes `unsupported_claim_type` (the sentence is precise; the tool lacks rank-change verification), c23 gains `scope: "2017"`. (4) The compiler now also raises `no_data` (G7, year rankings withheld as a stopgap for partial-year coverage), so NO_DATA is no longer engine-only. Interviewer question: why is "took the lead" unsupported rather than ambiguous, when the spike called it ambiguous?
- 2026-09-06 — Stage 3: the abstention table was written and reviewed before any compiler code, and the review changed it in ways code-first would have hidden: "took the lead" moved from `ambiguous` to `unsupported_claim_type` (the sentence is precise; the tool lacks rank-change verification — reasons are grouped by what the user can do, and a rewrite fixes nothing here), the calendar-year universe for time-grain rankings was replaced by an explicit `scope` field (an inferred universe was a false-PASS path for "second-best month of Q3"), and the owner's row V6 (baseline must precede the period) turned a swapped-period extraction from a silently wrong computation into an abstention. Evaluation order is itself a spec decision: schema gaps before vagueness, because c30 has both and only one is fixable in YAML. Interviewer question: your compiler never reads the span — so how does a sentence's *meaning* ever reach the verdict, and what does that say about where the LLM's job ends?
- 2026-09-06 — Stage 4: **a JSON-schema-constrained output guarantees shape, not meaning, and the shape can be silently wrong on my side.** Iteration 1 of the extraction eval rejected every comparison as `invalid_claim`: the flat wire schema had taken `direction` from the first Claim class declaring it (Growth), so the model was physically unable to emit `higher/lower/better/worse/unchanged` and wrote null or "decrease". The model had found the right span, metric and period every time. Fix: derive each shared field as the union of the per-class enums, pinned by a test; prompt untouched; both numbers kept (recall 0.9123 → 0.9649). Interviewer question: your eval improved after a change — how do you show it was a bug fix and not tuning to the test set?
- 2026-09-06 — Stage 4: **reject, don't repair.** A span that is not a verbatim substring, a duplicate span or id, a non-null field the type does not declare: each drops the claim into a `Rejected` record and its numbers fall to the sweep. Repairing (trimming a span, picking one of two duplicates, dropping a stray field) would let the extractor's guess reach a verdict through a side door, and a false PASS is the one unforgivable failure. Every accepted claim's span is therefore verbatim by construction, and the eval asserts it rather than measuring it. Interviewer question: what does a missed claim cost, who catches it, and why is that the safe side to fail on?
- 2026-09-06 — Stage 4: **precision is bounded by label granularity.** Seven "spurious" claims: four are true assertions the labeler never labeled ("record-breaking fourth quarter", vague growth), three are numeric halves of sentences the model split finer than the label ("...to stretch to 14.28 days" → comparison + point_value). Zero hallucinations, because a hallucinated span cannot survive the substring check. The 20 labels Stage 5 adds need a split rule written down before they are labeled, or the next precision number is not comparable to this one.
- 2026-09-06 — Stage 5, AMENDMENTS (visible, not silent), from the row-by-row review of docs/benchmark.md: (F4) seven labels gain `clean_span` because their report.md span never occurred in report_clean.md (the six corrupted claims, plus c42 whose verb changed when the spike split c41's sentence); the claim objects are untouched. (J4) CLAUDE.md §0 now says what the "no dataset in prompts" wall protects: the verification path. The eval-only judge receives a deterministic aggregate summary of the public example data, in bench/baseline_judge.py only, so the comparison is fair. (C2) `src/recount/cli.py` exists with only `bench`, a Stage 6 preview forced by pyproject already naming the entry point. Interviewer question: why is handing the judge the answer key the conservative choice for the comparison, not the generous one?
- 2026-09-06 — Stage 5, pre-live finding F-1 from the oracle run (perfect extraction, docs/benchmark.md §5): **the stated precision is lost at the float boundary.** A drifted "6.00%" arrives as the float 6.0; `half_ulp_tolerance` normalises it to zero decimals and grants ±0.5, so 6.00 vs 5.9662 PASSes. Three rounding_drift variants false-accept this way before a single live call. Not fixed: I2 requires a ruling and a changelog entry first. The candidate fix reads the decimals off the numeric token in the verbatim span, which is text reaching a verdict through the schema-validated Claim, the one door the walls allow. Interviewer question: a JSON number cannot say "6.00"; where in a typed pipeline does written precision survive, and who owns that field?
- 2026-09-07 — Stage 5, CHANGELOG 1 (visible; docs/benchmark.md §6): **a JSON-schema-constrained output only promises the keys you mark required.** The rate limits pushed the benchmark onto `gemini-3.1-flash-lite`; behind the owner's honesty gate it scored recall 0.5965 with `subject` omitted on 55/55 objects and `value`/`direction`/`period` omitted by type, so 21 claims were rejected and 17 state figures were verified against the national total. Making every wire key required-but-nullable (post-validation untouched) took it to recall 0.8947 / precision 1.0 / subject 28/28; the default model re-measured like for like held recall 0.9649. The default pin did not change; the benchmark states its own model (C7). Interviewer question: the fix lives entirely in the schema, not the prompt — why is that the only kind of extractor change that leaves the eval comparable, and what would a prompt edit have cost?
- 2026-09-07 — Stage 5, CHANGELOG 2 (visible; docs/benchmark.md §6): **written precision has to travel with the number, and a float cannot carry it.** The oracle run predicted three false accepts before any live call ("6.00%" → float 6.0 → zero decimals → ±0.5), the live run reproduced them, and only then, as ruled, did `stated_decimals` start reading the decimals off the verbatim span. Exact-match false accepts 3/100 → 0/100, nothing else moved, no new calls. Interviewer question: you fixed the verifier after seeing the benchmark — how is that not tuning to the test, and what in the repo lets someone check?
- 2026-09-07 — Stage 5 results, the interview-grade sentence: **83% detection on exact-match classes with 0 false accepts and 0 false flags on the clean report, against a judge that says "unfaithful" to everything including the clean report.** Two open findings matter more than the headline: the extractor can launder a fabricated metric into a real alias (F-2, 2/20, invisible to any verifier), and a one-token change elsewhere in a report can flip an untouched sentence's claim type at temperature 0 (F-4, 85 collateral false flags on 48 variants, 0 on the clean run). Interviewer question: which of those two would you fix first, and why is the answer not the bigger number?
- 2026-09-07 — Stage 5: **the class with 0% detection is the one I am proudest of.** Every wrong_ranking variant was extracted, every one abstained `schema_gap` because "secured the second position overall" names no measure and the config defines no `overall performance`. Coverage 100%, detection 0%, false accepts 0. Adding a config alias after seeing the table would have turned 0% into 100% and would have been the T10 move; it is written down as F-3 and left to the owner. Interviewer question: when is a 0% detection rate evidence the tool is working?
